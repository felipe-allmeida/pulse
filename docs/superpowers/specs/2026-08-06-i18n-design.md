# Pulse — Internationalization (pt-BR / en-US) — Design Spec

- **Status:** Approved design, pending implementation plan
- **Date:** 2026-08-06
- **Scope:** Frontend (UI chrome + data-driven content) and a small backend change (AI assistant answers in the user's language). No changes to presence/dashboard data flow, deploy, or the realtime backend.

---

## 1. Purpose

Make the whole pulse experience available in **English (`en`, default)** and **Brazilian Portuguese (`pt-BR`)**: the UI chrome, the data-driven content (bio, experience, project descriptions), and the AI recruiter chat (which answers in the user's active language). English is the default because the audience is international recruiters; Portuguese serves Brazilian visitors. The language is auto-detected on first visit, switchable via a header toggle, and remembered.

---

## 2. Decisions (locked)

- **Library:** `react-i18next` + `i18next` + `i18next-browser-languagedetector` (mature, Vite-friendly, the React standard). No URL-based locale routing.
- **Locales:** `en` (default/fallback) and `pt-BR`.
- **Detection order:** `localStorage` → `navigator.language` → fallback `en`. The user's explicit choice (toggle) is persisted to `localStorage` and wins on subsequent visits.
- **Toggle:** a compact, accessible **PT / EN** control in the header next to `ThemeToggle`.
- **Scope = UI + content + assistant.** Everything translatable is translated. The **AI assistant answers in the active locale** (system-prompt instruction; `profile.md` stays English as the grounding source).
- **Translations drafted by the assistant, reviewed by Felipe** — especially the Ulbra project copy (already de-identified/high-level; low risk, but Felipe confirms).
- **The projects' confidentiality invariant stays structural** — `visibility`/`links` remain on the typed data module (untranslated), so the existing invariant test keeps guarding it regardless of locale.

## 3. Architecture

```
web/src/i18n/
  index.ts            # i18next init: resources, detection order, fallback 'en', react-i18next binding
  locales/
    en/  common.json nav.json dashboard.json about.json projects.json ask.json
    pt-BR/ common.json nav.json dashboard.json about.json projects.json ask.json
  use-localized.ts    # hook resolving LocalizedString content fields by active locale
```

- **Init** in `web/src/i18n/index.ts`, imported once at app entry (`main.tsx`) before render. `LanguageDetector` with `order: ['localStorage','navigator']`, `lookupLocalStorage: 'pulse.lang'`, `caches: ['localStorage']`, `fallbackLng: 'en'`, `supportedLngs: ['en','pt-BR']`, `load: 'currentOnly'` (so `pt-BR-*` still maps to `pt-BR`), non-supported → `en`.
- **`<html lang>`** is kept in sync with the active locale (accessibility/SEO) via an effect in `AppShell` (or the toggle).

### 3.1 UI chrome (t-keys)
Every hardcoded user-facing string in these components moves to a namespaced key read via `useTranslation('<ns>')`:
- **nav:** `nav/top-nav.tsx`, `nav/cv-button.tsx`
- **dashboard:** `kpi-row.tsx`, `stat-card.tsx`, `live-map.tsx`, `visits-chart.tsx`, `recent-visits-table.tsx`, `event-feed.tsx`, `reactions.tsx`, `connection-status.tsx`, `presence-badge.tsx`
- **about:** `about/about-hero.tsx`, `about/experience-timeline.tsx`, `about/skill-groups.tsx`, `about/social-links.tsx`
- **projects:** `projects/project-card.tsx`, section headings in the projects route
- **ask:** `ask/ask-widget.tsx` (intro, suggested questions, input placeholder, AI disclaimer, error line)
- **common:** shared labels (loading, retry, empty states, "online", units)

Interpolation (`t('key', { count })`) + i18next plurals for counts (e.g. "1 visitor" / "N visitors", "N online"). Number/relative-time formatting uses `Intl` with the active locale (the chart/table timestamps and counts).

### 3.2 Content (data-driven)
The typed content modules keep their **structure**; only human-readable text becomes locale-aware.

```ts
// web/src/content/types.ts
export type Locale = 'en' | 'pt-BR';
export type LocalizedString = Record<Locale, string>;
```

- `content/profile.ts` — `name` stays a plain string; `title`, `tagline`, `bio`, and each `experience[].role/summary` (and any prose) become `LocalizedString`. Structural bits (`social[].href/label`, `skills[].items`) stay as-is (skill names are proper nouns; group labels become `LocalizedString` or a t-key).
- `content/projects.ts` — `slug`, `tech`, `links`, `visibility`, `screenshot?`, and `name` stay untranslated (`name` is a product proper noun — "pulse", "Ulbra Atende"; structural bits are **where the confidentiality invariant lives**). `tagline`, `description`, `role`, `period?` become `LocalizedString`.
- **`use-localized.ts`** — `const L = useLocalized(); L(project.description)` returns the string for the active locale (falls back to `en` if a `pt-BR` value is empty). Components call `L(...)` on content fields; UI chrome uses `t(...)`.

This keeps the invariant test (`content.test.ts`) valid (it asserts `visibility`/`links`, which don't change) and puts all translatable copy in one reviewable place.

### 3.3 AI assistant (answers in the active locale)
- **Frontend:** `lib/ask.ts` sends the active locale in the `POST /api/ask` body (`{ question, history?, locale }`); `ask-widget.tsx` passes `i18n.language`.
- **Backend:**
  - `AskEndpoints.cs` request DTO gains an optional `Locale` (validated against an allow-list `["en","pt-BR"]`; anything else → `en`).
  - `AskMessageBuilder.cs` appends a system instruction: *"Respond in {English|Brazilian Portuguese}, regardless of the language of the profile below."* The `profile.md` stays English (single grounding source); only the response language changes.
  - The guardrail/grounding/injection-resistance instructions are unchanged; the language line is appended server-side (never client-controlled beyond the locale enum).
- Keyless/`NullAiClient` path unaffected (its canned "not configured" message can also be localized via the two known strings).

---

## 4. Toggle component

`web/src/components/i18n/language-toggle.tsx` — a small shadcn control (a two-item segmented control or a `DropdownMenu` with PT/EN), `aria-label`, keyboard-navigable, visible focus. Calls `i18n.changeLanguage(lng)` (which persists via the detector's `localStorage` cache) and updates `<html lang>`. Mounted in `app-shell.tsx` next to `ThemeToggle`. Shows the active language; switching re-renders all `t()`/`L()` consumers instantly (no reload).

---

## 5. Testing

**Frontend (vitest + testing-library):**
- i18n init: unsupported/absent → `en`; `pt-BR` detected from a mocked `navigator`/localStorage resolves to pt-BR resources.
- `language-toggle`: renders both options, switching calls `changeLanguage`, persists to `localStorage`, and flips rendered text (assert a known string in both locales).
- A representative component (e.g. `top-nav` or `ask-widget`) renders the pt-BR string when the locale is pt-BR.
- `useLocalized`: returns the active-locale value and falls back to `en` when a `pt-BR` field is empty.
- `content.test.ts` (existing) still passes — the public/private invariant is untouched.
- `lib/ask.ts`: the request body includes `locale`.
- Test harness: a small `renderWithI18n(ui, { locale })` helper wrapping `I18nextProvider` (mirrors the existing router-wrapper test pattern).

**Backend (xUnit):**
- `AskMessageBuilder`: given `locale = "pt-BR"`, the assembled system messages include the "respond in Brazilian Portuguese" instruction; given `en` (or unknown/absent), the English instruction; the profile text + guardrails are still present.
- `AskEndpoints`: an out-of-allow-list `locale` is coerced to `en` (no error); the streamed response path is unchanged (fake `IAiClient`).

**Hard gate:** `pnpm -C web build` + `pnpm -C web exec tsc --noEmit` + `pnpm -C web test` green; `dotnet build` + `dotnet test` green.

---

## 6. Content translation (pt-BR)

The assistant drafts pt-BR for **all** UI keys and content fields. Felipe reviews:
- Tone/idiom (natural pt-BR, not literal), technical terms kept where idiomatic (e.g. "deploy", "backend").
- **Ulbra project copy** — the pt-BR must stay as high-level as the English (product/role/stack only), no proprietary detail. Same confidentiality bar as the English.
- `profile.md` stays English (the assistant's grounding); the *response* is localized at request time.

---

## 7. Scope (YAGNI)

**In:** `en`/`pt-BR`; react-i18next setup + detection + persistence; header toggle; all UI chrome keys; localized content modules + `useLocalized`; assistant responds in-locale; tests; drafted pt-BR translations. **Out:** URL/path-based locale (`/pt/...`), a 3rd language, RTL, a translation-management platform, server-rendered locale, localizing `profile.md` itself, date-library beyond `Intl`.

---

## 8. Success criteria

- First visit auto-detects the browser language (pt-BR browser → Portuguese, otherwise English); the header toggle switches instantly and the choice sticks across reloads.
- UI chrome **and** content (bio/experience/projects) render fully translated in both locales; nothing shows a raw key or an English fragment in pt-BR mode (except intentionally-untranslated proper nouns/skills).
- The AI chat answers in the active language while staying grounded in the English `profile.md` (no fabrication; injection resistance intact).
- The projects' public/private confidentiality invariant is unchanged and still test-guarded.
- All hard-gate checks green.
